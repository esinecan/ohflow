# Operate a run

Use this procedure for every fresh workflow run and campaign run.

## Run beside another session in a dedicated clone

`preflight` reads the checkout that the workflow names as its repository, and two of its checks fail on another session's work there. `clean tree` fails when `git status --porcelain --untracked-files=no` prints a line, so an uncommitted edit to a tracked file stops the run and an untracked file does not. `base branch` fails when the checkout is on any branch other than the workflow's base branch. Never commit, stash or switch away another session's work to pass them. Give the run a clone of its own. Below, `<checkout>` is the working checkout, `<clone>` the run's clone and `<base>` the base branch.

1. **Clone from the remote.** Run `git clone -c core.longpaths=true "$(git -C <checkout> remote get-url origin)" <clone>`, and `git -C <clone> checkout <base>` when the base branch is not the remote's default. Clone the remote's URL and not the checkout's path: a step on an ssh box or a cloud box pushes its transport branch to the clone's `origin`, which must be the hosted remote. A clone does not inherit the checkout's local git settings, and on Windows a worktree whose path passes 260 characters fails to check out unless the repository sets `core.longpaths`; the `-c` writes it into the clone, and Git on macOS and Linux ignores it. When the run must start from commits that `<checkout>` holds on `<base>` and has not pushed, run `git -C <clone> pull --ff-only <checkout> <base>`. A fresh clone holds one local branch, so when a worktree starts from another branch (`WorktreeSpec.base`), run `git -C <clone> fetch <checkout> <branch>:<branch>` for it. Done when `git -C <clone> status --porcelain` prints nothing and `git -C <clone> log -1 --oneline` shows the commit the run starts from.
2. **Point the workflow at the clone.** Pass the clone as the workflow's repository, and give every worktree a path outside both `<checkout>` and `<clone>`, for example `--args repo=<clone> --args worktree=<clone>-wt/<name>`. The `--out` runs root stays where it is. Run `preflight --workflow <module> --args ...` with the run's arguments. Done when it prints `PREFLIGHT PASS`. Then follow the sections below.
3. **Fetch each worktree's branch into the checkout before `revert`.** The run's commits sit on the branch of each worktree (`WorktreeSpec.branch`; `<run-dir>/revert.json` lists them). `revert --run <run-dir>` deletes those branches together with their worktrees, so fetch first: `git -C <checkout> fetch <clone> <branch>:<branch>`. The fetch writes the branch and touches no file of the checkout, so it is safe while the other session works. For a pull request, run `git -C <clone> push origin <branch>` instead or as well. Done when `git -C <checkout> log --oneline <base>..<branch>` lists the run's commits.
4. **Merge only with the user's go.** `git -C <checkout> merge <branch>` merges into the branch the checkout is on and changes its files under the other session. Git refuses the merge and changes nothing when an uncommitted file overlaps the branch (`Please commit your changes or stash them before you merge`); then leave the branch unmerged and name it to the user. Done when the branch is merged, or the user has its name and the reason it waits.
5. **Take the run out of the clone.** Run `revert --run <run-dir>`: it removes the run's worktrees and branches from the clone. Keep the clone for the next run and refresh it with `git -C <clone> pull --ff-only`, or delete its folder. Done when `git -C <clone> worktree list` shows the clone alone.

## Hand the user the dashboard

When a run transports hashed text artifacts between Windows and a cloud worktree,
set their Git line-ending policy before capture. Use `-text` for hashed raw evidence
that must travel byte for byte. For normalized text, combine `text eol=lf` with a
writer that explicitly emits LF (Python's `write_text(..., newline="\n")`, for example).
A checkout rule alone does not stop a Windows writer from emitting CRLF before the
hash is taken. Verify the hash after an independent checkout, not only in the worktree
that captured the file.

A run that `run` starts has a live dashboard. `--no-dashboard` and `--dry-run` start none, and roll-call test cases run without one. The user monitors the run there and gets its URL first.

1. **Fire with `--hold`, or with `--pilot` when the workflow declares units, and hand over the URL.** Run `run --hold ...`. For a workflow with `Workflow.units`, run `run --pilot --history <runs root> ...` instead. The run writes its plan, serves the dashboard, passes preflight and waits; the page reads `held` and every step opens its plan (brief, tool policy, write scope, limits). Read `dashboard: <url>` on line one and send the user the link inside the bill that [monitor-a-run](monitor-a-run.md#at-hand-over-write-the-bill) describes. A detached run may print `dashboard: pending`; read `<run-dir>/dashboard.json` later. With `--pilot`, the smallest unit of each unit path runs first, in `<run-dir>\pilot`. Call `watch --run <run-dir>` until it prints `held: waiting for go`. Then put the projection into the bill: the `pilot:` line, each `pilot <path>:` line and the `ESTIMATE` line beside them. Wait for the user's go or revisions. Edit the workflow module when the user asks. After an edit, run `estimate --workflow <module> --args ... --pilot <run-dir>` and hand the user the new projection. `go` loads the module again. Then run `ohflow go --run <run-dir>`, and add `--predictions <file>` when you wrote an orchestrator calibration during the hold: `go` writes the file to `predictions.md`, logs it in `notes.md`, and refuses when `predictions.md` already holds predictions. Done when `go` has printed `go sent to <run-dir>`.
2. **Watch the run by [monitor-a-run](monitor-a-run.md).** It covers each poll, each phase boundary and each of the user's replies. Done when `watch` exits with a code other than 10.
3. **Close with the exit report.** Give the user the verdict and the `exit report:` path. Done when the user has both.

For a campaign, call `campaign watch` and send the user each new dashboard URL. `campaign run --hold` holds the first fresh round only, and a later round whose estimate exceeds the first round's actual minutes by half ([campaign](campaign.md)).

## Keep the run notes

Every fresh run writes four notes at its root: `predictions.md`, `notes.md`, `retro.md`, `ground-truth.md`. Contract: [ohflow](ohflow.md#four-run-notes-sit-at-the-run-root).

1. **Write an orchestrator calibration when the user asks for one.** Answer the five lines of the `predictions.md` template yourself, from the workflow module and its briefs, before you run `ohflow estimate` and before any result. Line 2 asks which steps will burn the most wall time and tokens: count what each step repeats, such as a full suite per step, a fix loop after every edit or a review of every piece, and say why it costs what it costs. Then run `ohflow estimate --workflow <module> --args ... --history <runs root>` and hand the user your five lines beside its numbers: the run's p50 and p80 minutes and tokens, and the sample count per phase. The user reads your lines for rigor that is mis-sized, too strict for its benefit or too loose for its risk. Fire with `run --predictions <file> --history <runs root>`, so the run writes `estimate.json`, and the retro compares your lines with what happened. Done when all five lines have an answer and you wrote them before reading the estimate or any step result.
2. **Log every manual action.** Resume, pause, kill, brief edit, hand fix, overruled gate, surprise: run `notes log --run <run-dir> "<text>"`. Done when every such action has a line.
3. **Close with the retro.** After the exit report, walk the user through the pointers in the drafted block. Fill "What I judge" with the user: their verdict per step, whether the gate was right, the cause. In section 1 of `ground-truth.md`, link the CI run on the pushed head unless the merged head has the gated tree, whose recorded pass `notes check` accepts. Done when `notes check` reads `NOTES COMPLETE`.
